# Ручной вывод подарками и компактная навигация

## Статус PR

**Черновик для проверки, не подтверждение выполнения всего исходного большого задания.**
Рабочая база: main после PR #52 (`7f3de428`). Production не изменялся.

## Реализовано

- Четыре пункта навигации, новые оригинальные изображения, Market без изменений.
- Компактный профиль; общий вход «Сделки и чаты», вкладки, карточки активных сделок,
  unread, поддержка и информация. «Ещё» и «Настройки» удалены из UI, старые ссылки перенаправляются.
- Кошелёк открывается кнопкой `+`; в нём доступны пополнение, вывод и сохранённые заявки.
- Сервер получает `getAvailableGifts`, выбирает доступные неограниченные непремиальные
  подарки. Нет захардкоженных ID/цен. Нет автоматических вызовов `sendGift`.
- По бюджету из заработанных AF подбирается максимальная достижимая стоимость подарков,
  затем минимальное количество подарков для этой стоимости.
- `gross_af = ceil(payout_stars / 0.70, 2)`, `fee_af = gross_af - payout_stars`.
  Резервируется gross, а не весь введённый бюджет. Пример при доступном подарке за 15:
  бюджет 30 AF → подарок за 15 Stars, резерв 21.43 AF, комиссия 6.43 AF, остаток бюджета 8.57 AF.
- Состав подарков и расчёт хранятся в PostgreSQL. Quote действителен 5 минут;
  перед резервом перепроверяются каталог, принадлежность quote и заработанный баланс.
- Quote ID уникален для заявки: повторный запрос не создаёт новый резерв даже после
  перезапуска или завершения заявки. Резерв/возврат/списание выполняются с блокировкой
  строки кошелька внутри DB transaction. Клиент не задаёт фактическую комиссию/стоимость.
- Существующие статусы сохранены: pending → approved → paid; rejected/cancelled
  возвращают полный ещё не выданный резерв. Paid ставит только администратор.
- Администратору через существующий outbox приходит состав выдачи, ID пользователя,
  комиссия, резерв и ссылка на конкретную заявку. Повторные решения не создают
  повторные операции/уведомления. Пользователь видит статус сервера, не ложную выплату.
- При частично выполненной **ручной** отправке администратор не должен нажимать
  «Отклонить»: необходимо вручную завершить сверку/выдачу. Система не проверяет
  факт отправки подарка из личного аккаунта администратора.
- Новые продажи автомобилей: 100% продавцу, комиссия продажи 0%. Обучение сохраняет
  отдельную настройку (по умолчанию 70%). Исторические завершённые сделки не пересчитываются.

## Миграции и запуск

- `0038_manual_gift_withdrawals`: новая `gift_withdrawal_quotes`; в `withdrawal_requests`
  добавлены nullable `gift_quote_id` (unique FK), `fee_af`, `payout_stars`, `gift_plan`.
  Старые заявки сохранены и обслуживаются прежним admin decision flow.
- `0039_car_sale_zero_fee`: payout=price, commission=0 только для незавершённых сделок
  с полным резервом и без записей settlement в ledger. Завершённые, отменённые и
  несогласованные/уже рассчитанные строки не меняются. Последние требуют отдельного аудита.
- Миграции forward-only, без удаления рабочих таблиц/истории.
- Применение: из `backend` выполнить `python -m alembic upgrade head` штатным Railway workflow.
  Локально проверена генерация PostgreSQL SQL, не применение на production.
- `BOT_TOKEN` и `DATABASE_URL` остаются серверными переменными.
- `SELLER_PAYOUT_PERCENT=100`; старая переменная со значением 70 не включает комиссию
  автомобилей обратно. `TRAINING_SELLER_PAYOUT_PERCENT=70` задаётся отдельно;
  если ранее для обучения был другой процент, укажите именно прежний процент.
- `PAYOUT_NFT_THRESHOLD_STARS=350`: верхний предел стоимости обычных подарков на одну
  заявку (диапазон настройки 1–5000). Остаток бюджета не резервируется.
  Полноценный маршрут NFT-заявки здесь не реализован.
- Старые POST без quote получают понятный 409: сначала открыть обновлённую форму расчёта.
  Старые строки БД и маршруты просмотра/решения не удалены.

## API

- Новый `POST /api/withdrawals/quote`: `{amount}` → quote ID, срок, gross, fee, payout, остаток, план.
- `POST /api/withdrawals`: `{quote_id, details}` → существующая/новая заявка пользователя.
- `GET /api/withdrawals`, `GET /api/profile`, `GET /api/admin/withdrawals`: добавлены поля расчёта.
- `POST /api/withdrawals/{id}/cancel`: возврат резерва pending-заявки владельцу.
- `POST /api/admin/withdrawals/{id}/{approve|paid|reject}`: серверная admin-проверка,
  идемпотентный повтор того же статуса, запись ledger и outbox.
- Deep link `admin_withdrawal_id` открывает соответствующую карточку в admin-панели.
  API по-прежнему проверяет роль; ссылка не предоставляет дополнительных прав.

## Что осталось от исходного большого задания

- Публичные сообщения администратора участникам сделки и новая стилизация этих сообщений.
- Полная история сделок с карточками товара: текущая вкладка истории переиспользует историю операций.
- Полная ревизия раздела Информации, новый стиль продвижения, NFT-заявки.
- Показ фактической даты последнего изменения сделки независимо от времени последнего сообщения.
- Реальный двухаккаунтный Telegram E2E, включая повторный вход и сохранение delivery ID.
- Автоматическую отправку подарков **не добавлять**: пользователь уточнил ручной процесс.

До слияния на production требуется тестовая Railway/PostgreSQL проверка миграций и
ручного сценария выдачи. Черновик PR не следует воспринимать как гарантию «всё работает».
