# Жизненный цикл сделок — локальная проверка, 7 сентября 2026

## Статус приёмки

Реализация находится в `agent/deal-lifecycle-safety`, основана на main `a0a7727`.
PR #51 уже был слит до начала этой задачи. Эта работа не переоткрывает его и не меняет production автоматически.
**Приёмка не завершена: обязательный Telegram/Railway E2E двумя реальными аккаунтами пока не проведён.**
Нет предоставленного тестового Railway/PostgreSQL, реальных Telegram-сессий покупателя/продавца или устройств iPhone/Android.
Реальные платежи, возвраты и сообщения production-пользователям не запускались. Секреты в код не добавлялись.

## Найдено и изменено

- Передача могла запускаться первым нажатием. Теперь передача, получение и отмена требуют отдельного modal, по умолчанию фокус на отмене. Повторные нажатия блокируются до окончания запроса.
- Напоминание было одноразовым. Новый серверный цикл хранит раунд и следующий срок в БД. Первый запрос подтверждения отправляет существующий worker, а не дополнительная BackgroundTask.
- Завершение, отмена и решение спора использовали недолговечные фоновые отправки. Уведомления сохраняются в существующем transactional outbox; параллельная повторная отправка из routes удалена.
- Обращение поддержки и остановка напоминаний фиксируются одной транзакцией. Открытие формы не создаёт спор.
- Добавлены защищённая админ-панель конкретной сделки и журнал событий. Финансы по-прежнему обслуживает `resolve_dispute`, а не новый расчёт баланса.
- Админское решение проверяет резерв объявления и структуру защищённых средств; повторный `request_id` возвращает уже выполненный результат. Другая операция на закрытой сделке не выполняется.
- Возврат через новую панель после заявленной передачи оставляет объявление `paused`; до передачи оно возвращается в `active`. Физического удаления нет.
- В старом endpoint решения обращения найден незавершённый read transaction перед `session.begin()`. Чтение заканчивается до входа в финансовый сервис, который повторно проверяет обращение под блокировками.
- Валидный `successful_payment` теперь допускает локально `expired` invoice. Валюта XTR, владелец, сумма и уникальность Telegram charge остаются обязательными. Pre-checkout просроченного invoice по-прежнему отклоняется.
- Сетевая ошибка больше не утверждает, что платёж получен. Исправлена маршрутизация `?view=profile` и добавлен `?admin_deal_id=...` с серверной проверкой роли.
- Обновлены статьи о сделке, отмене и поддержке. Никакой автоматической выплаты по истечении времени нет.

## Состояния и действия

Названия БД сохранены; `transfer_in_progress` соответствует ожиданию подтверждения покупателя.

| Состояние | Покупатель / продавец | Администратор / выход |
| --- | --- | --- |
| `paid`, `seller_contacted` | Данные передачи, чат; обе стороны могут отменить. Продавец отмечает передачу после заполнения данных | Полный возврат, завершение с выплатой, проверка, комментарий |
| `transfer_in_progress` | Обе стороны видят сделку и чат. Покупатель подтверждает после существующей паузы 60 секунд либо создаёт обращение. Обычная отмена запрещена | Проверка, полный возврат или завершение с выплатой, комментарий |
| `disputed` | Чат/поддержка доступны; средства остаются в резерве, напоминания прекращены | Возврат, выплата, комментарий; возобновление незавершённого спора только после закрытия активных обращений |
| `completed` | История сохраняется; активный чат закрыт, объявление продано | Только комментарий; повторная выплата запрещена |
| `cancelled` | История и возврат сохраняются; активный чат закрыт | Только комментарий; повторный возврат запрещён |
| `pending_payment`, `buyer_confirmed` | Сохранены совместимые значения CHECK. Текущая обычная покупка создаёт сразу `paid`, подтверждение атомарно завершает сделку | Не переинтерпретируются массовой миграцией. Наличие старых зависших записей требует read-only аудита рабочей БД |

Частичный возврат не добавлен: в текущей модели нет согласованных правил распределения частичного возврата/комиссии.
Закрытая финансовая сделка не открывается заново. Возобновить можно только спор с ещё существующим резервом. Для отмены уже выполненной выплаты нужен отдельно согласованный компенсационный процесс.

## Таймеры, перезапуск и доставка

- Существующий seller-response timeout 24 часа и возврат неактивного продавца сохранены.
- Покупателю: сразу после отметки передачи, затем через 2 часа, ещё через 4 часа (6 часов суммарно), далее каждые 12 часов от предыдущей попытки/доставки.
- Состояние хранится в `deals`: после рестарта worker читает сроки из PostgreSQL. Старое `sent` и зависшее `sending` восстанавливаются с отложенным следующим раундом, без немедленного повторения неоднозначно доставленного сообщения.
- После 48 часов без зафиксированного действия сделка помечается `needs_admin_review_at`, администратору ставится одно уведомление. Сообщения участников учитываются как действия; напоминания не сбрасывают эскалацию. Выплаты нет.
- После обращения, отмены или завершения напоминания о подтверждении не отправляются.
- Абсолютная exactly-once доставка через внешний Telegram API не обещается: после неоднозначного сетевого результата используется существующая политика outbox, а не бесконечный replay.

## Архитектура, API и миграция

- `deal_lifecycle.py`: запись событий, расписание, восстановление и нефинансовые решения администратора.
- `DealEvent` / `deal_events`: событие, участник, переход статуса, контекст, request_id, время. Уникальность `(deal_id, request_id)`.
- `deals`: добавлены `buyer_reminder_round`, `needs_admin_review_at`. Старые сделки/пользователи/кошельки не удаляются.
- Миграция `0037_deal_lifecycle`, после `0036_inactivity_state`: только ADD COLUMN / CREATE TABLE / CREATE INDEX. Downgrade запрещён, чтобы не удалять аудит; откат структуры — только проверенной forward migration.
- Журнал событий начинает заполняться с этой версии, не выдумывает прошлые события. Старые даты сделки, сообщения и финансовая история показываются отдельно.
- `GET /api/admin/deals/{deal_id}/control`: участники, резерв, даты, действия, события, обращения, ledger, последние 200 сообщений.
- `POST /api/admin/deals/{deal_id}/control`: `action`, `reason` минимум 5 символов, UUID `request_id`. Действия `complete/refund/review/resume/comment`. Авторизация admin на сервере.
- Существующие `/deals/{id}/transfer`, `/confirm`, `/cancel`, `/support` и admin resolve сохранены.

## Выполненные тесты

- 259 backend-тестов, включая 11 новых проверок с SQLite-персистентностью и HTTP:
  выплата и полный возврат через админский сервис, повтор request_id, запрет повторного открытия;
  отмена каждой стороной до передачи; запрет отмены после передачи;
  неуспешное/успешное создание обращения и остановка напоминаний;
  восстановление расписания, одна эскалация без движения денег;
  внутренний комментарий, запрет доступа обычному пользователю;
  late expired Stars invoice, повтор charge, неверная валюта/сумма.
- 81 frontend-тест, включая проверку упрощённого профиля.
- `deal-lifecycle-browser.cjs`: Edge с API fixtures на 320/360/390/430 — modal, отмена, двойной tap, один POST, сохранение экрана сделки после обновления, `?view=profile`.
- `navigation-browser.cjs`: те же ширины, safe areas, resized composer, back, точный чат/read receipt/badge.
- `compact-ux-browser.cjs`: публичный интерфейс тех же размеров без Telegram-авторизации.
- Alembic имеет один head; PostgreSQL SQL новой миграции сгенерирован offline. Это **не** применение миграции к реальной PostgreSQL.
- SQLite и тестовые заглушки Telegram не доказывают PostgreSQL lock/concurrency, restart Railway или живую оплату Stars.

## До слияния / запуска в production

1. На отдельном тестовом Railway применить `cd /app/backend && python -m alembic upgrade head`; проверить единственный head и worker после restart.
2. Двумя реальными аккаунтами проверить покупку, случайное нажатие/отмену modal, передачу, видимость чата, первое и повторное уведомления.
3. Создать обращение со скриншотом, убедиться в остановке напоминаний и уведомлении администратора с точной сделкой.
4. На разных тестовых сделках проверить полный refund и выплату, повторный API request и конкурентный запуск. Сверить резерв и единственные ledger-записи в PostgreSQL.
5. Проверить seller cancellation до передачи, отсутствие права отмены после передачи.
6. Перезапустить тестовый Railway, проверить сроки/историю и отсутствие дублей. Проверить валидный запоздалый `successful_payment` только в разрешённой тестовой платёжной среде.
7. Проверить реальные iPhone/Android Telegram WebView, поддержку modal, клавиатуру, safe areas и deep links.

## Дополнение: упрощение профиля

По следующему запросу пользователя оставлены только Пополнение, Мои объявления, История сделок, Диалоги, Обновить данные профиля и Администратор (admin-only). Это одна компактная группа действий. Ссылки на помощь/поддержку/настройки убраны из профиля, не перенесены в другие разделы. Существующие экраны и backend этих функций не менялись из-за упрощения профиля. Убраны отдельный блок замороженных средств и крупная админская карточка; сокращены отступы пустых состояний. История показывает существующие сделки и операции, не меняя финансовые сервисы.

Иконки нижней навигации, в том числе Market, не менялись: четыре новых изображения пока не предоставлены.
`profile-simple-browser.cjs` проверяет пять действий пользователя / шесть администратора, переключения разделов, refresh и topup, отсутствие переполнения и размеры кнопок на 320/360/390/430 px. Используются явные API fixtures, не реальные Telegram-аккаунты.
Дополнительно изменены тесты `webapp/tests/compact-ux.test.cjs`, `webapp/tests/ux-navigation-history.test.cjs`; добавлен `webapp/tests/profile-simple-browser.cjs`.
