# Подтверждение передачи и получения автомобиля

Ветка: `agent/deal-transfer-confirmation`, база: main после PR #60.
Миграций, новых env и новых финансовых правил нет.

## До / после

Статусы БД не переименовывались:

`paid / seller_contacted → transfer_in_progress → completed`

- `transfer_in_progress` уже означает отметку продавца и ожидание покупателя,
  а не выплату. Это назначение сохранено.
- Раньше общее окно закрывалось до запроса, ошибки показывались вне окна.
  Повторный успешный запрос возвращал конфликт.
- Теперь продавец и покупатель получают отдельное окно подтверждения с
  loading/error/success. Отмена, Escape, Telegram Back и фон ничего не отправляют.
- Новое окно не подтверждается вторым тапом исходного двойного нажатия:
  первые 450 мс подтверждение заблокировано. Отправка дополнительно защищена
  флагом выполняющегося действия в приложении и состоянием компонента.
- После ответа сервера показана галочка, через 800 мс начинается закрытие
  длительностью 200 мс. При ошибке окно остаётся открытым для повтора.
- Сохранена существующая серверная задержка 60 секунд после отметки продавца
  перед подтверждением покупателя. Комиссии, сроки возвратов и поддержка не менялись.

## API, деньги и конкурентность

Изменены сервисы существующих маршрутов (новых endpoints нет):

- `POST /api/deals/{deal_id}/transfer` → `set_deal_status`.
- `POST /api/deals/{deal_id}/confirm` → `complete_deal`.

Оба пути используют существующую Telegram-авторизацию, транзакцию и
`SELECT FOR UPDATE` конкретной сделки. Состояние перечитывается из БД,
проверяется роль, статус, отсутствие завершения/отмены.
Перед первым переходом проверяются резерв объявления, положительная стоимость,
сумма источников escrow и наличие удержанных средств в кошельке.

Продавец не списывает, не возвращает и не начисляет деньги.
Повтор его запроса в `transfer_in_progress` возвращает сохранённый результат,
не обновляет время, не создаёт новые события/уведомления.
После отмены/завершения продавец получает 409. Посторонний пользователь — 403.

Покупатель подтверждает только после сохранённой отметки продавца. Завершение
использует прежние `consume_purchase_hold`, `credit_sale_proceeds`,
порядок блокировок кошельков, комиссию и разделение обычных/бонусных AF.
Повтор покупателя после его собственного завершения возвращает результат без
второго payout. Завершение администратором не считается таким повтором.

Существующий аудит `status_changed` / `buyer_confirmed` сохранён.
Добавлены `seller_marked_transferred` и `order_completed` в DealEvent с timestamp.

## Уведомления

Первое уведомление покупателю по-прежнему отправляет существующий durable worker,
из очереди в Deal, с конкретным `deal_id` и переходом к получению/поддержке.
Текст дополнен просьбой проверить машину на указанном игровом ID.
Повтор seller-confirm не создаёт второй слот отправки.
Плановые напоминания через существующие интервалы сохранены — это не дубли запросов.

После получения продавец получает существующее transactional-outbox уведомление:
покупатель подтвердил получение, сделка завершена, фактически начисленная сумма.
Реальная доставка зависит от доступности Telegram и того, не заблокирован ли бот.

## Проверки

- Backend: 400 тестов, в том числе 22 новых; с отдельным PostgreSQL на localhost
  и одноразовыми схемами, не production. Проверены сохранение escrow после продавца,
  одна выплата после покупателя, прямой HTTP API, роли, неоплаченные/закрытые статусы,
  некорректный резерв, отсутствие отметки продавца, повторы.
- 8 параллельных seller requests → одна отметка. 8 buyer requests → один payout.
  4 конкурентных запуска существующего отправщика → одна отправка первого
  уведомления (Telegram transport в тесте подменён, PostgreSQL настоящий).

  В дополнительном стресс-тесте обнаружен конфликт с повтором покупки:

### Ограничения проверки

Это не тест на настоящих телефонах и не реальная покупка в Telegram.
Браузер использует явно обозначенные API/SDK fixtures только в тестах.
Перед production rollout нужны два тестовых Telegram-аккаунта и реальный
iPhone/Android: отменить передачу, затем подтвердить, получить уведомление,
открыть конкретную сделку, подтвердить получение, сверить баланс/историю.

Общий `tsc --checkJs` старых `api.js/app.js` не проходит из-за существующих
неописанных глобальных API и типов. Полного настроенного project typecheck/
frontend lint в репозитории нет; это не исправлялось массово в данном PR.
Строгая проверка нового компонента проходит.
Docker/Railway image здесь не собирался: локального Docker нет.
Выполнен production frontend build из того же скрипта, который запускает Dockerfile.
