# Сделки продавца, мобильный интерфейс и аналитика владельца

## Объём

Изменение существующего проекта, база — main / PR #81. Без production-платежей, массовых сообщений, автодеплоя или слияния. Четыре фотографии от 02.11.2026 использованы как визуальные ориентиры, не вставлены картинками в интерфейс. Тестовые скриншоты содержат только явно тестовые данные.

## Сделка продавца

Новый webapp/js/seller-deal.js используется существующим чатом:

1. paid, продавец не принял: центрированная инструкция и «Принять сделку».
2. Принято, ID отсутствует: реальный серверный deadline, напоминание об ID.
3. ID указан: ID/копирование, deadline, «Машина передана» открывает существующее confirmation-окно.
4. transfer_in_progress: ожидание покупателя, ручное напоминание; escrow не превращается в доступный заработок.

Завершённые, отменённые и спорные сделки не показывают устаревшие действия. При новом конечном статусе запрашивается свежий профиль/баланс. Существующие seller accept, buyer cancellation, transfer, buyer receipt и расчёт не переписаны. Возврат через 24 часа без передачи сохранён, принятие срок не перезапускает.

Обнаружен дефект фонового обновления: GET /conversations/{id} вызывался без deal_id, хотя открытие и сообщения были привязаны к сделке. Область запроса исправлена; запоздалый ответ другой сделки той же переписки отбрасывается. Это подтверждённая ошибка кода, не доказательство единственной причины всех предыдущих чёрных экранов на физических iPhone.

Новые API:

- GET /api/deals/{id}/reminders — срок следующего ручного напоминания, только продавец.
- POST /api/deals/{id}/reminders/id|receipt, тело с UUID request_id.

Блокировка строки Deal, аудит DealEvent и существующая уникальность request_id защищают повтор и конкурирующие устройства. При повторе возвращается прежний результат, частота ограничивается сервером. Уведомление идёт через существующую durable Notification-очередь и открывает нужную сделку. Устаревшие уведомления подавляются; уже ожидающее автоматическое напоминание о получении не дублируется ручным. Ошибка Telegram не меняет деньги или статус сделки.

## Мобильные жесты

На UI-поверхности .app-shell и внешние диалоги установлен touch-action: pan-x pan-y; в сообщениях сохранён pan-y. Нет глобальных touch/gesture preventDefault, maximum-scale=1 или user-scalable=no. Сохранены поля 16 CSS px, keyboard/safe-area/visualViewport, системное масштабирование текста и браузерный клавиатурный zoom. Это следует модели прямых жестов [Pointer Events](https://www.w3.org/TR/pointerevents/#the-touch-action-css-property).

Отдельного pinch-просмотрщика фотографий в текущем проекте не обнаружено, новый просмотрщик не создавался. Если он появится, его поверхность должна находиться вне ограничивающего UI-контейнера; потомок не может отменить ограничение предка. Физический pinch в Telegram iOS/Android требует проверки на устройствах. Headless WebKit не выдаётся за такую проверку.

## Финансы

backend/app/owner_finance.py, новая вкладка существующей админки webapp/js/owner-finance.js.

- GET /api/admin/finance — фильтры start/end/timezone/all_time, limit 1–100, offset; по умолчанию 25 операций.
- GET /api/admin/finance/referrals — до 10 лидеров.
- Доступ: только admin с Telegram ID, равным существующему ADMIN_ID; другой admin и support не получают доступ. Отсутствующий owner ID не открывает доступ всем.
- После авторизации отчёт использует один repeatable-read READ ONLY snapshot. Нет записей в ledger или правок баланса.
- Exact Decimal-строки, AF и Stars раздельно, евро не вычисляются. Поступление Stars и признанный доход — разные категории, не суммируются.
- VIP берётся из окончательного ledger-списания, не из reservation, платежа и уведомления одновременно.
- Публикация признаётся только по связанной подтверждённой оплате и опубликованному черновику. Неисполненные оплаты показаны отдельно.
- Собственные автомобили — только завершённые продажи аккаунта владельца, не всех администраторов/продавцов.
- Обучение: подтверждённый оборот, рассчитанная доля платформы, зачисления владельцу и другим авторам отдельно. Возврат исключает комиссию такой покупки до сверки, а не создаёт выдуманное распределение частичного возврата.
- 30% не комиссия пополнения. Доход вывода берётся из сохранённого fee_af исполненной заявки с ledger-списанием, не по новой формуле.
- Выплаты Stars — подтверждённые администратором завершения; это не независимая выписка Telegram. В открытых частично выполненных заявках показывается полный номинал, детали остатка остаются в заявке.
- Снимок доступных и frozen wallet-бакетов — текущие обязательства. Открытые выводы — часть этих резервов, не второе слагаемое.
- Топ рефералов считает реальные уникальные qualified relations. Сначала агрегирует награды и отношения отдельно: число приглашений не умножается на число наград. Различает начислено и подтверждённое ledger-зачисление бонусных AF. Ссылки валидируются, ограничения приватности tg:// явно указаны.
- Никаких случайных чисел. Если расходы/полученные владельцем внешние выплаты не учтены, чистая прибыль = null и объяснение, а не «ноль затрат».

### Ограничения данных

Неизвестны приобретение/конвертация Stars, хостинг, налоги, внешние расходы и выводы владельца. Отдельной надёжной даты возврата Stars нет: отчёт показывает возвращённые платежи когорты поступлений периода, а не притворяется календарным банковским cashflow. Исторические NULL fee не восстановлены по современному калькулятору. Неподтверждённые старые покупки обучения не засчитываются как оплаты. Ledger-операции оборота/распределения/поступления нельзя просто сложить.

## Market

Собственная аватарка — доступная кнопка существующей навигации в Profile, включая fallback без фото. «Сердечки» были настоящими ListingLike, отдельно от Favorite. Их данные и API сохранены; дизайн заменён на SVG большого пальца. Кнопки ожидают серверный ответ, блокируют повторный запрос, снимают лайк по DELETE. Уникальность на сервере не изменена; лайки не создают финансовых операций.
