# Публикация объявлений: аудит и исправления

## Подтверждённые причины

1. `api.upload` и выбор фото в `app.js` отклоняли исходник по транспортному лимиту **до сжатия**. Значения расходились: frontend/server по умолчанию 30 MiB, `.env.example` — 20 MiB.
2. WebView декодировал оригинал целиком, только затем проверял разрешение. Дополнительно превью открывали все оригиналы одновременно. Это подтверждённый риск памяти, **не доказанная причина конкретного production-инцидента**.
3. JPEG создавался с одним значением качества, без проверки готового размера и адаптивных попыток.
4. Потерянный ответ загрузки оставлял новую копию изображения при повторе. У публикации уже был request ID; сама загрузка не имела дедупликации.
5. Пустые после trim строки, слишком большие числа и явный `null` в PATCH могли доходить до БД вместо понятного 422.
6. При редактировании обычного объявления VIP был автоматически выбран.
7. Ссылку на несуществующий/чужой `/api/media/{id}` можно было передать в публикацию или оплачиваемый черновик.

Исторический `AF-2Q1P4Q3U`: логов нет, точная причина **не установлена**. Навык управления подключениями подтвердил, что Railway не подключён; повторное предложение подключения не отправлялось, поскольку оно уже было недавно. Токены и production-данные не читались.

## Что изменено

- Ограниченное чтение заголовка JPEG/PNG до декодирования в браузере. До 16 MP — уменьшение до 2560 px, JPEG с несколькими ступенями качества/разрешения; неизвестные размеры и тяжёлые форматы идут в ограниченный серверный декодер. HEIC/HEIF/AVIF не требуют ручной конвертации.
- Исходный размер и допустимый размер отправки — разные проверки. MIME/расширение не являются доказательством содержимого. SVG/документы не превращаются в разрешённый JPEG.
- Фото загружаются последовательно при выборе. Превью показывают сохранённые серверные JPEG 480 px, а не десять многомегапиксельных оригиналов. Ошибка одного фото сохраняет остальные URL, поля и порядок; есть отдельный retry. Публикация ждёт успешных загрузок.
- Сервер обрабатывает `UploadFile.file` напрямую, без дополнительной полной копии исходника в RAM. Изображения нормализуются в JPEG, удаляются EXIF/GPS, корректируется ориентация/прозрачность. Первое изображение анимации/многостраничного файла становится фото.
- UUID сохранённого изображения определяется владельцем и SHA-256 нормализованного содержимого. Первичный ключ PostgreSQL защищает от параллельных дублей; другая учётная запись получает другой ID. Исходные опубликованные URL не переписываются.
- До multipart parsing действует ограничитель общего тела и двух одновременных загрузок на процесс. Декодер работает последовательно вне event loop. Multipart spool закрывается при успехе, ошибке и превышении chunked-лимита.
- Нормализованные фото хранятся в существующей PostgreSQL-таблице, не на эфемерном диске Railway. Неиспользуемые временные multipart-файлы удаляются закрытием spool. **Сохранённые изображения в БД автоматически не удаляются**: старые ссылки могут оставаться в платных черновиках, сделках и истории; опасный сборщик мусора не добавлен.
- Проверка принадлежности/существования новых DB-media URL перед публикацией, оплатой черновика и VIP-резервом. Старые внешние URL и `/uploads/...` оставлены совместимыми; их доступность этим изменением не гарантируется.
- Валидация trim, диапазона целых, Decimal(18,2), запрет явного null обязательных PATCH-полей. Цена передаётся строкой без предварительного округления JavaScript.
- VIP при редактировании выключен по умолчанию; существующий активный VIP не снимается. Ошибки публикации получают диагностический код, а не только ошибки фотографии.

## Лимиты и конфигурация

| Этап | Лимит |
|---|---|
| Исходник в Mini App | 64 MiB, до 10 фото |
| Декодирование в браузере | известные JPEG/PNG до 16 MP, canvas до 2560 px |
| Отправка | `UPLOAD_MAX_BYTES`, новый default/example 67108864 (64 MiB) |
| Multipart envelope | транспортный лимит + 128 KiB |
| Серверное разрешение | 64 MP |
| Готовый JPEG | цель ≤1 MiB; жёсткий максимум 2 MiB; сторона ≤2560 px |
| Превью | сторона ≤480 px |
| Время | браузерный запрос 90 s; получение тела сервером ≤120 s; очередь ingress 5 s |

Действующее значение `UPLOAD_MAX_BYTES` в Railway **не известно и не изменялось**. Если там осталось 20/30 MiB, большие HEIC/AVIF или фото, переданные на сервер без клиентского декодирования, всё ещё будут ограничены этим значением. Перед релизом установить согласованные 67108864, проверить proxy/timeouts и RAM на staging. Наличие лимита пикселей не гарантирует достаточную память любого Railway-тарифа; для 48–64 MP нужен замер RSS на целевом контейнере. Production deploy не выполнялся.

## Экономика и данные

Правила не менялись: 5 активных слотов CP1+CP2; шестой — серверная цена (default 5 Stars). Зарезервированная оплаченная продажа остаётся занятым слотом до завершения. Удаление/завершённая продажа освобождают слот. VIP — отдельная опциональная покупка; редактирование бесплатно.

Использованы существующие `Listing`, `ListingImage`, `UploadedImage`, `PublicationDraft`, `ListingPromotion`, `StarPayment` и ledger. Новых таблиц/полей/миграций нет. Атомарность/восстановление платной публикации остаются в действующих `publications.py`/`services.py`; тесты добавлены поверх них, а не вместо них. Нет реальных списаний, пополнений, возвратов или выплат.

API: расширен `GET /api/uploads/policy`; `POST /api/uploads` теперь оптимизирует/дедуплицирует и закрывает spool; `GET /api/media/{id}?preview=true` отдаёт маленькое превью. Existing POST/PATCH listing/publication/VIP routes получают дополнительную проверку фотографий. Форматы ответов публикации не изменены.

## Проверки

Локально: 506 backend passed, 129 skipped (нет локальной PostgreSQL + отдельный browser gate); 111 Node passed; Ruff изменённых Python файлов (`E701,E702` исключены как существующий стиль), JS syntax, production build и `git diff --check` прошли.

Реально проверены обработка JPEG/PNG/WebP/HEIF/AVIF/GIF/BMP/TIFF, неверные MIME/расширения, ориентация, прозрачность, повреждения, SVG/PDF/HTML, 48 MP JPEG и настоящие BMP 20/30/50 MiB. Проверены ограничения тела включая chunked и закрытие временных файлов.

Браузерные fixtures: 320/360/390/430 px, неудача второго фото, сохранение формы, retry только неудавшегося, отсутствие повторной публикации; CP1/CP2, редактирование без VIP/новых фото, отсутствие overflow. Это эмуляция, **не физические iOS/Android Telegram**.

Новые PostgreSQL-тесты: 1/5/10 фото, CP1/CP2, параллельная загрузка/публикация, чужое/отсутствующее фото, профиль и другой пользователь, редактирование/замена, переподключение приложения и БД, шестая платная публикация, сохранённый receipt при сбое и восстановление с повторным событием без повторного платежа.

Новый отдельный CI browser gate: настоящий frontend → подписанный Telegram initData → настоящий HTTP backend → изолированная PostgreSQL; потеря уже успешного POST-ответа, повторный тап, 1/10 фото, бесплатное редактирование и просмотр покупателем. Telegram WebApp shell эмулируется; API ответов-заглушек нет. Результат CI дополняется после фактического запуска.

Не проверены: живой Stars checkout, production-логи и настройки, реальные исходники ошибки AF-2Q1P4Q3U, физические устройства и медленная мобильная сеть; чисел production не выдумывали.

## Релиз и rollback

1. Review PR; зелёный CI с PostgreSQL и browser gate.
2. Staging: текущая копия схемы, согласованный upload limit, реальный iPhone/Android, исходные фото владельца; замер памяти и проверка reverse proxy. Проверить тестовый Stars checkout на отдельном боте.
3. Backup и **отдельное разрешение владельца** на production deploy.
4. После релиза смотреть `image_upload_stage/completed/failed/guard`, `listing_publish` по AF-коду, stage/status/size/duration/decoder class; без initData, токенов, содержимого фотографий.
5. Rollback — предыдущий commit приложения; миграции откатывать не нужно. Сохранённые JPEG и UUID совместимы с предыдущим `/api/media` маршрутом. Не удалять `UploadedImage`, оплаченные черновики и payment receipts.

Документация сверялась с установленными библиотеками: Pillow 11.3.0, pillow-heif 1.1.0, FastAPI 0.116.1, текущий локальный Starlette parser. Первичные справки: [Pillow](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html), [Starlette multipart](https://starlette.dev/requests/), [Railway public networking](https://docs.railway.com/networking/public-networking). Документация Railway не подтверждает параметры конкретного сервиса владельца.
