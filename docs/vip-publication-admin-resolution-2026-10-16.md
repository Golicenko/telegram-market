## 1–4. Публикация с VIP: подтверждённая причина и исправление

На исходном коде воспроизведено для CP1 и CP2 при достаточном балансе:

1. `create_listing()` создаёт объявление и запись списания `WalletTransaction`.
2. `record_balance_pin()` добавляет `ListingPromotion` со ссылкой `ledger_id`.
3. На общем flush SQLAlchemy вставляет promotion раньше ledger. PostgreSQL
   отклоняет INSERT: `listing_promotions_ledger_id_fkey`, отсутствует связанная
   запись `wallet_transactions`.
4. Транзакция целиком откатывается. Объявления и списания не остаётся.
5. Обработчик `IntegrityError` дополнительно обращался к истёкшему после rollback
   атрибуту `seller.id`, маскируя исходную причину исключением `MissingGreenlet`.

Без VIP этот участок не исполняется. Отдельная покупка VIP через используемый
интерфейс `/vip/orders` идёт через `finish_locked()`, где ledger уже записывался
до ссылки на него. Поэтому отдельное закрепление могло работать.

Исправление: явный `flush()` ledger **в той же транзакции**, до создания promotion;
это не промежуточный commit. Тот же порядок исправлен в старом AF-only
`charge_listing_promotion()`. ID продавца для восстановления после rollback
захватывается заранее как скаляр.

Нехватка AF не оказалась причиной воспроизведённой ошибки. Существующий 402 с
`purpose=listing_promotion` по-прежнему открывает существующую доплату. Форма,
загруженные фотографии и идентификатор сохраняются. VIP-заказ резервирует AF,
подтверждённый Stars receipt покрывает недостающее, worker атомарно публикует VIP.
Отмена освобождает резерв; UI не сообщает об успешной публикации.

Платная публикация сверх лимита и VIP остались разными услугами: отдельный
`PublicationDraft`/Stars receipt и отдельная оплата VIP. Подтверждённая публикация
не требует повторной оплаты при потере ответа. Переход из оплаченного черновика
в VIP-modal больше не сопровождается исключением «публикация не удалась».

`finishListingSubmission()`, `payPublication()` и `payListingPromotionShortfall()`
отделяют серверный результат от последующего GET/обновления UI. Ошибка обновления
не превращается в ошибку уже сохранённой публикации или оплаченного VIP.

## 5–7. Администратор/поддержка: подтверждённая причина и результат

Исходный `POST /api/admin/support/tickets/{id}/resolve` воспроизведён с настоящей
подписанной авторизацией и PostgreSQL: **HTTP 500, но Deal=completed и продавцу
уже начислено 100 AF**. Сам финансовый commit в этом тесте успешен.

`SupportTicket.updated_at` обновляется через `onupdate=func.now()`. После UPDATE
атрибут истекает даже при `expire_on_commit=False`. Повторный `session.get()`
возвращает тот же объект из identity map. Синхронная сериализация Pydantic
пытается прочитать истёкший атрибут и выполнить async I/O: `MissingGreenlet`.
Теперь перед сериализацией явно выполняется `await session.refresh(ticket)`.
Отдельный тест воспроизводит истёкший `updated_at` и прежнюю ошибку сериализации.

В UI поддержки POST и перезагрузка списков прежде попадали в один catch.
Теперь подтверждённое завершение показывается отдельно от ошибки обновления:
«Сделка успешно завершена. Средства начислены продавцу. Данные не удалось
обновить. Попробуйте открыть раздел заново».
Подтверждённая карточка сразу становится решённой; кнопки повторной выплаты
не остаются активными даже при ошибке последующей загрузки списка.

Для управления сделкой результат перезагрузки также учитывается отдельно.
Нет новой модели расчётов: обе формы используют существующий `resolve_dispute()`.

**Это не доказательство результата конкретной production-сделки владельца.**
Для неё нужны ID сделки/обращения, время, журнал ledger и логи соответствующего
запроса. По воспроизведённой ошибке нельзя начислять деньги ещё раз вручную.

## 8. Защита от повторных операций

- Во всех трёх путях решения используется существующий `DealEvent.request_id`.
  `/resolve` и поддержка принимают необязательный request_id, старые клиенты
  совместимы; новый UI отправляет его и сохраняет при неоднозначном ответе.
- Проверяется actor, действие, причина и связь с обращением. Повтор того же
  решения возвращает текущий результат без ledger/event/notification-дубликатов.
- Новый запрос к закрытой сделке получает 409, отсутствующая сделка — 404.
  Конфликт не объявляется успешным решением.
- Сохраняются блокировки Listing → Deal → Wallet; два админа не выполняют две
  выплаты. Финансы, статус, аудит и уведомления фиксируются атомарно.
- После timeout/network/5xx/невалидного ответа UI читает существующий admin control
  и ищет точное событие request_id/actor/action/reason. Только это подтверждает
  операцию. Один статус completed без совпавшего события недостаточен.
- Проверка согласованности резерва теперь одинакова для control, resolve и
  поддержки. Возврат после отмеченной передачи не возвращает товар автоматически
  в активную продажу: используется существующее безопасное состояние paused.
- Прямое решение через `/resolve` также закрывает связанные активные обращения.

## 9. Ошибки и диагностика

Существующий `ApiError` сохраняет HTTP status, machine-readable detail, endpoint
и AF-код. Известные ошибки переводятся в русский текст. Обработаны 400/401/402/
403/404/409/413/415/422/429/500/502/503/504, network, timeout, отмена и invalid JSON.
402 VIP предлагает доплату; 422 указывает поле; 409 не означает автоматически
«уже опубликовано». Неизвестный результат не выдаётся за успех.

SQL, traceback, HTML прокси и неизвестные внутренние исключения не показываются
пользователю. Технические причины остаются в серверных логах и диагностике.
Ошибка обновления после commit имеет отдельный диагностический контекст.

## 13. Что нельзя подтвердить без production

Нет подключённого Railway/logs/production DB; текущие значения env, deployed SHA
и результат именно тех пользовательских операций не проверены. Нужны временной
интервал, AF-код, ID сделки/обращения или client_request_id публикации и read-only
запросы к соответствующим ledger/events. Секреты и токены в чат не нужны.

Браузерные тесты — Chromium mobile viewport, подписанная тестовая авторизация,
тестовая оболочка Telegram. Это не физический iPhone/Android и не настоящий
Telegram Stars checkout. Bot API-доставка уведомлений на реальные аккаунты не
проводилась; проверены сохранение и отсутствие дубликатов outbox-записей.

## 14. Выпуск, сохранность и rollback

PR не сливается и production не выкатывается автоматически. После review:
обычный backup, staging с текущими config, обе цепочки, затем согласованный deploy.
Контролировать 5xx, AF-коды, состояние VIP и admin решения; при необходимости
откатить код на предыдущий образ. Миграционного rollback нет.

Откат кода не отменяет уже проведённые операции — их нельзя выполнять повторно.
Сверять ledger перед ручным вмешательством. VIP-сроки, карточки, фотографии,
комиссии, слоты, выводы, рефералы и пользовательские данные массово не менялись.
