# Активные публикации, отмена заказа и поддержка

## Обнаружено и изменено

1. Публикация опиралась на `User.publication_count` за всё время. Теперь единый
   `publication_quota.py` считает обычные объявления CP1 и CP2 вместе:
   активные/зарезервированные без удаления, плюс объявления с оплаченной
   незавершённой сделкой и удержанием (`paid`, `seller_contacted`,
   `transfer_in_progress`, `disputed`). Окончательная продажа/удаление/снятие
   освобождает слот, если нет активного удержания. Исторический счётчик сохранён.
2. Проверка и создание используют один `User FOR NO KEY UPDATE`. Два запроса
   при четырёх слотах не создают шестую бесплатную публикацию. Проверка того же
   продавца добавлена в административное восстановление снятого объявления.
   Существующая возможность снять модерацию остаётся только у администратора;
   пользователь не получает возможность самовольно вернуть скрытый товар.
   При заполненных слотах административное восстановление получает 402:
   нужно освободить слот либо продавцу оформить новую платную публикацию.
3. При пяти и более слотах используются прежние PublicationDraft, XTR invoice,
   successful_payment, recovery и возврат через администратора. Старые оплаченные
   черновики сохраняют цену. Первоначальная цена по действующей конфигурации — 5 Stars.
   Старые объявления (в том числе 16 и больше) не трогаются, задним числом не оплачиваются.
   Редактирование остаётся бесплатным, удаление платной публикации не возвращает Stars.
4. Если слот освободился, неоплаченный черновик можно опубликовать бесплатно.
   Во время принятого pre-checkout действует прежняя 15-минутная защита.
   Запоздалый платёж уже бесплатно опубликованного черновика сохраняется в
   существующей очереди `publication_review` для возврата лишнего платежа;
   второй товар и AF по нему не создаются.
5. Ранее поддержка отправляла администратору общее фоновое Telegram-сообщение,
   а темы отображала как сохранённые технические ключи. Теперь 11 категорий и
   legacy aliases находятся в одном серверном справочнике. UI получает их через API;
   английские ключи в старых строках БД не переименовываются.
6. Общие обращения можно связать с собственным заказом, без обязательного
   скриншота и без изменения финансового статуса. Формальный спор из сделки
   по-прежнему использует существующий endpoint, скриншот и блокировку средств.
   Общие вопросы не переиспользуются как финансовые споры и не закрываются
   автоматически финансовым решением по другому обращению.
7. Создание общего обращения защищено клиентским request ID и блокировкой
   автора; повторная отправка/перезагрузка не создаёт новое уведомление.
   Первое сообщение хранит ключ в существующем `SupportMessage.client_request_id`.
8. Новое уведомление содержит номер, настоящий username (или явно его отсутствие),
   русскую тему, ограниченный фрагмент сообщения, ссылку на обращение, контакт,
   ссылку на связанный заказ. Используется прежняя durable outbox, не второй sender.
   Подтверждение пользователю и ответы также идут через эту очередь.
   Telegram `unknown` не переотправляется вслепую; `blocked`/ошибки сохраняются.
9. Ссылка без username — `tg://user?id=…`: зависит от приватности Telegram,
   не гарантирует личный чат. Всегда есть «Связаться через бота», открывающая
   существующую форму ответа поддержки. Если бот заблокирован, сообщение остаётся
   в Mini App, а доставка через Telegram невозможна до разблокировки.

## Аудит отмены — финансовый код не переписан

`cancel_deal` уже использует Listing → Deal → Wallet locks, проверяет участника,
статус и принятие продавцом, возвращает все компоненты удержания один раз.
Повторный запрос получает 409 без повторного возврата. Продавец не может принять
уже отменённый заказ; принятие и отмена сериализованы. После принятия доступна
поддержка, но самостоятельная отмена запрещена. После завершения отмена запрещена.

**Важно о текущем SLA:** текущая main отправляет принятый, но не переданный
заказ после 24 часов в `disputed` / `accepted_delivery_overdue`, деньги удерживаются
для проверки. Без принятия — действующий возврат. Автовыплаты продавцу по таймеру нет.
Это отличается от более раннего пожелания о возврате даже после принятия.
В этой задаче действующее финансовое правило не изменено; владельцу следует
отдельно подтвердить нужное правило перед последующей финансовой правкой.

## API и хранение

- `GET /api/publication-rules`: `active_count`, `used` теперь активный count,
  `remaining`, `payment_required`; исторический `publication_count` не источник квоты.
- Существующие `/api/listings`, `/api/publication-drafts/*`, admin publish:
  новые проверки слотов, прежняя платёжная цепочка.
- `GET /api/support/categories`: 11 русских тем, иконка, признак связи с заказом.
- `POST /api/support/tickets`: optional `deal_id`, `client_request_id`, проверенная тема.
- Ticket responses: `topic_label`, `public_number`, admin-only `contact_url`.
- Номер обращения — стабильное короткое представление существующего UUID
  (8 символов), не новая последовательная нумерация и не Telegram ID.
- Миграции не нужны. Новых таблиц/колонок нет. Старые обращения, платежи,
  объявления и ledger не удаляются.

## Проверки и ограничения

Добавлены PostgreSQL сценарии для 0/4/5/10/16 активных, истории 100 публикаций,
CP1+CP2, удаления/продажи/паузы, настоящего завершения тестовой сделки,
конкурентной новой/повторной публикации, оплаты и позднего webhook.
Существующие тесты invoice, rollback, повторов и финансовой отмены сохранены.
Добавлены тесты категорий/переводов/длинного текста, доступа к чужим обращениям,
повторов создания и ответа, Telegram markup, ссылки без username и истории.
Браузерные сценарии: 320/360/390/430px, форма публикации и поддержки.

Проект использует обычный JavaScript; отдельного TypeScript typecheck нет.
Проверки: `node --check`, Node tests, pytest, Ruff и production asset build.
Фактические результаты полного прогона фиксируются в PR после CI.

Реальные iOS/Android Telegram WebView, настоящая доставка ботом и live Stars
checkout пока не проверены: @Lunoj указан как личный аккаунт, не тестовый бот;
адрес staging не предоставлен. Fixtures используются только в тестах, не в продукте.
На production не выполнялись покупки, списания, возвраты, отправки или миграции.

## Релиз и откат

После PostgreSQL CI и review развернуть сначала staging, проверить два аккаунта
и доставку уведомления. Затем обычный deploy. Новых env нет; используются текущие
BOT_TOKEN, PUBLIC_BASE_URL и роли/список сотрудников поддержки.
Контролировать outbox failed/unknown/blocked, paid publication drafts и ошибки 402.
Откат к предыдущему коммиту не требует обратной миграции и сохраняет историю,
но вернёт старую пожизненную квоту и старую доставку общих обращений. Уже созданные
pending support notices остаются в совместимой очереди. Не переотправлять sent/unknown
массово и не откатывать БД для отката UI.
