# AutoFlow: фото, отмены, выводы, VIP и информация

Дата: 2026-10-15. База: main после PR #72. Production не развёртывался; реальные оплаты, возвраты, подарки и отправки ботом не выполнялись.

## Причины и исправления фотографий

Доказан воспроизводимый дефект: маленький валидный AVIF открывается Pillow 11.3.0, но прежний `normalize_image_content` отвергал его кодом 415 из-за allowlist. Превью допускало любой `image/*`, а клиентская конвертация выполнялась только для JPEG/PNG/WebP > 8 МБ. Поэтому результат зависел от реального формата и размера, а не только от телефона. Аналогичное расхождение было у GIF/BMP/TIFF.

Это НЕ доказывает, что конкретный код `AF-2Q1P4Q3U` был вызван именно AVIF: нет исходного файла и подключённых Railway-логов. Код AF — случайный идентификатор запроса, не кодек/тип ошибки. Railway найден среди доступных интеграций, но не подключён; CLI также недоступен. Для расследования конкретного инцидента нужны события `image_upload_failed`/client diagnostics по этому ID из Railway.

Изменения:

- Сервер декодирует настоящее содержимое и пересохраняет JPEG: JPEG, PNG, WebP, HEIC/HEIF, AVIF, GIF, BMP, TIFF. Многокадровые изображения — первый кадр. HTML/SVG/PDF и повреждённые данные не выдаются как фото.
- Клиент проверяет сигнатуру перед canvas, пробует конвертацию и небольших изображений, включая AVIF и нестандартный MIME. Не умеющий HEIC WebView передаёт оригинал серверному декодеру. Неподдерживаемые произвольные данные не превращаются в «разрешённое фото» на основании расширения.
- Размер файла: текущий `UPLOAD_MAX_BYTES` (по умолчанию 30 МБ); policy endpoint синхронизирует форму. Жёсткий предел декодирования — 64 MP, включая обычные 48 MP фото. Серверная обработка одного изображения за раз ограничивает пиковую память; выход не больше 2560 px по стороне.
- Исправляется EXIF-ориентация, метаданные не переносятся, прозрачность заполняется белым. Ресайз до EXIF-копии уменьшает расход памяти.
- Ошибки 413/415/422 теперь сохраняют конкретную безопасную причину сервера. Логи содержат диагностический ID, этап, MIME, размер, тип ошибки декодера; не initData/токен/содержимое файла.
- Ошибка одного фото не очищает описание или выбор. Можно убрать только одно фото, повторить его загрузку или добавить новые файлы. Отмена picker не сбрасывает выбор.
- Уже сохранённые фото повторно не отправляются при повторе публикации. Перед публикацией браузер загружает сохранённое `/api/media/...`, проверяя доступность. Неопределённый сетевой ответ не вызывает финансовое действие.
- Пока все фотографии не сохранены, ни публикация, ни её платёж не запускаются. Существующий `client_request_id` и блокировка кнопки защищают повторную публикацию.

Ограничение существующей платной публикации: Stars checkout предшествует коммиту объявления. Если сервер падает уже ПОСЛЕ подтверждённой оплаты, действующий durable draft восстанавливает публикацию; после повторных неудач она попадает на admin review, где есть возврат `refundStarPayment`. Нельзя честно обещать отсутствие временно оплаченного, но ещё не опубликованного черновика. Этот механизм не заменён и тарифы не изменены.

## Отмены и расчёт продавцу

До принятия: `paid → cancelled`, весь резерв возвращается в исходные purchased/earned/bonus категории; чат архивируется, обеим сторонам записывается уведомление. Сервер сериализует отмену и принятие по блокировкам сделки/объявления. Повторная отмена даёт 409 и не возвращает деньги снова.

После принятия (`seller_accepted_at`, legacy `seller_contacted` или transfer timestamp) самостоятельная отмена запрещена. После отметки передачи средства ещё в escrow. Получение подтверждает только покупатель; действует существующая 60-секундная защита после отметки передачи. Финальный settlement выполняется один раз.

Текущее main: неответивший и не принявший продавец — допустимый возврат через срок backend (по умолчанию 24 ч.); принятый, но не переданный заказ — admin review с удержанием, не ошибочный «первоначальный неответ». Спорные/переданные/закрытые сделки не отменяются этим сценарием. Правила отмены и сроки в этом PR не менялись.

## Вывод заработанных AF

Для новых продаж автомобиля код начисляет 100% цены, без комиссии продажи. Бонусная часть оплаты остаётся бонусной у продавца, не становится выводимой. Для старой финансовой истории не переписываются прежние суммы.

Вывод — ручная отправка подарков, НЕ автоматическая выплата Stars на личный баланс. Каталог — существующий `getAvailableGifts`; сумма зависит от реальных доступных подарков. Комиссия 30% включена в резерв (`gross`), не удерживается второй раз при завершении. Бюджет 30 AF при подарке 15 Stars: резерв 21.43 AF, комиссия 6.43 AF, 8.57 AF не резервируются. Округление вверх до копейки сохраняет прежнюю модель.

Добавлен `gift_deliveries` — записи уже произведённых ручных отправок: gift ID, количество, стоимость из сохранённого плана, уникальный request ID, подтверждение отправки, actor, UTC timestamp. Запись НЕ отправляет подарок и НЕ списывает AF. Оставшийся резерв удерживается до завершения всей заявки.

- Одобренную заявку можно исполнять частями; прогресс/остаток видны пользователю и админу.
- Повтор того же запроса не добавляет запись; другой payload с тем же ID/повторное подтверждение отправки отклоняются.
- Нельзя записать лишнее количество, чужой подарок или изменить сохранённую стоимость.
- После первой частичной отправки нельзя отклонить заявку с полным возвратом. Нужно сверить и отправить оставшиеся подарки; произвольного механизма частичного денежного возврата не добавлено.
- При учёте частями «Подарки отправлены» доступно только после записи всех подарков. Общий прежний сценарий ручного подтверждения ВСЕХ подарков сохранён для заявок без частичных записей.
- Финальное списание резерва и уведомление — однократно через существующий `decide_withdrawal`. Последовательные публичные номера не менялись.
- «Профиль → 💸 Вывести средства» открывает ту же форму, что и «Баланс → Вывести заработанные средства».

Ранее отправленные вручную подарки у незавершённых заявок нельзя восстановить из пустой истории: администратору нужно сверить Telegram и записать фактические отправки перед любым отказом. Интерфейс явно предупреждает об этом. Старые продажи с уже удержанной комиссией также не пересчитываются автоматически: происхождение исторического заработка требует отдельной сверки, новый тест доказывает отсутствие двойной комиссии именно в новой полной цепочке.

## VIP-рамка

`webapp/images/vip-leaf-frame.png` — прозрачная рамка, полученная встроенным ImageGen из предоставленного JPEG (удалён нарисованный клетчатый фон). Сохранены прямоугольная форма и расположение золотых ветвей. Не используется как фотография автомобиля.

CSS добавляет отдельный `pointer-events:none` слой вокруг исходного `<img>`. Рамка масштабируется пропорционально в квадратной области; фото показывает `object-fit:contain`, без растягивания и изменения файла. Оформление автоматически включается у активного VIP по существующим полям и исчезает по истечению. Сроки, цены, покупки и продление 72 ч./10 Stars не изменены. Файл ~1.1 MB, общий для всех карточек, без постоянной анимации.

Prompt инструмента: “Extract ONLY the existing gold rectangular frame and its metallic gold leafy branches onto a genuinely transparent PNG alpha background. Remove ALL grey and white checkerboard squares, both inside and outside the frame, including spaces between leaves. Preserve the original precise gold shape, proportions, rectangular inner aperture, branch positions at top-left and bottom-right, fine leaf veins, metallic shading and edges. Do not redesign, add ornaments, text, car, shadow background, or enlarge branches. Keep the complete frame and every leaf visible with the same square canvas and original placement.”

## Не проверено / релиз и rollback

Нет живой проверки конкретного инцидента Railway, исходного проблемного фото, реального iPhone/Android Telegram, staging checkout/уведомлений. В браузерных тестах Telegram API и внешний ответ платежей — изолированные фикстуры. Не утверждаем «100% проверено».

Перед релизом: backup БД; rehearsal 0051→0052 на копии; staging загрузка HEIC/AVIF из реальной галереи, проверка ID/клавиатуры и читаемости рамки на телефонах. Только после отдельного разрешения — production deploy.

Rollback: сохранять additive колонку и историю. **Нельзя возвращать старый код обработки выводов, если есть approved-заявки с частичными отправками:** старый код не знает запрета полного возврата. Сначала сверить и завершить такие заявки либо оставить финансовые команды нового backend. Down migration преднамеренно запрещена, чтобы не потерять доказательства выплат. Восстановление backup не заменяет сверку уже вручную отправленных подарков.
